# TattvaTech CRM — Dream Build Specification

> **Document type:** Master product, engineering, UX, data, infrastructure, and implementation blueprint  
> **Primary purpose:** This file is the single source of truth for building the TattvaTech CRM / Company Workspace.  
> **Project status:** Planned / specification stage  
> **Primary deployment:** TattvaTech-controlled ASUS ROG server  
> **Version covered in depth:** Version 1, with explicit future-ready extension points  
> **Document philosophy:** Build only what TattvaTech actually needs, but design the foundations so the product does not collapse into spaghetti the moment the company grows beyond four people.

# 0. Non-Negotiable Decisions

These decisions are already finalized. A coding agent or developer working from this file must **not silently replace, expand, or reinterpret them**.

## 0.1 Fixed CRM application stack

The CRM application stack is:

- **Next.js**
- **TypeScript**
- **Tailwind CSS**
- **MySQL**
- **MinIO**

That is the fixed application stack.

### Explicitly not part of the CRM application stack

Do not introduce these unless the project owner later changes the decision:

- PostgreSQL
- Redis
- Prisma
- NestJS
- Express as a separate backend
- Supabase
- Firebase
- MongoDB
- GraphQL
- tRPC
- separate Python/Flask backend
- microservices for ordinary CRM modules
- external document database
- separate frontend and backend repositories

The intent is a focused, understandable system with one Next.js application acting as the application layer.

## 0.2 Email utility

**Nodemailer** is explicitly approved as the application email-sending utility.

It is not a replacement for the fixed application stack. It exists to allow the Next.js server-side application logic to send transactional and internal notification emails.

## 0.3 Version 1 finance entry is manual

In Version 1:

- financial transactions are manually entered by authorized users;
- this is intentional;
- TattvaTech's official business documents and formal financial setup are still being prepared;
- automatic bank transaction ingestion is therefore not a Version 1 dependency;
- the database design must still allow future automation without rewriting the entire Finance module.

## 0.4 Invoices are generated by the CRM and stored in MinIO

For a qualifying manually recorded client payment:

1. the user records the transaction;
2. the CRM validates and stores the transaction in MySQL;
3. an invoice is generated;
4. the invoice file is saved to MinIO;
5. the invoice metadata and MinIO object key are stored in MySQL;
6. the invoice becomes available from Finance, the relevant Client, and the relevant Project;
7. relevant emails are sent through Nodemailer.

## 0.5 TattvaTech core services belong on TattvaTech-controlled infrastructure

The current approximately 32 GB server is hosted on college-controlled infrastructure.

That server must **not** be treated as a dependable long-term home for TattvaTech's core systems because:

- TattvaTech does not control the college network;
- network switch changes during holidays already caused disruption;
- the company cannot make its own uptime depend on infrastructure decisions made by an unrelated institution;
- company-critical workloads should move to infrastructure TattvaTech can control.

The ASUS ROG server becomes the primary TattvaTech-controlled server for constant internal services.

## 0.6 Core services on the ASUS ROG server

The ROG should host the systems that are constant parts of the firm:

- TattvaTech company website;
- TattvaTech CRM / Company Workspace;
- MySQL for the CRM;
- MinIO for CRM documents;
- in the future, n8n;
- in the future, TattvaTech's own WhatsApp bot.

Temporary demos may also run on the ROG when resources permit.

## 0.7 Commercial SaaS / ERP production deployments

The long-term production model for sold SaaS/ERP products is:

- the real production product is deployed on infrastructure provided by or controlled by the client;
- TattvaTech's own infrastructure is not intended to permanently host every client's production system;
- TattvaTech infrastructure may host temporary demonstrations and proofs of concept;
- School ERP and College ERP demo environments can be spun up before sales meetings and shut down afterward.

# 3. Product Principles

## 3.1 One source of truth

WhatsApp is allowed to remain a communication channel.

It is **not** the canonical database for:

- lead stage;
- meeting decisions;
- pending follow-ups;
- proposal status;
- payment status;
- invoice status;
- project status;
- AMC status;
- technical incidents.

The CRM is the canonical source.

## 3.2 Every important entity needs history

Important records must have a timeline.

Examples:

- lead created;
- lead assigned;
- stage changed;
- meeting scheduled;
- meeting completed;
- note added;
- follow-up created;
- proposal uploaded;
- proposal sent;
- lead converted;
- client created;
- project created;
- payment recorded;
- invoice generated;
- invoice emailed;
- AMC payment recorded;
- task completed;
- incident created.

## 3.3 Fewer screens, richer records

Do not build dozens of isolated forms whose data cannot be traced.

The important unit is the record:

- Lead
- Client
- Project
- Invoice
- Transaction
- AMC
- Meeting
- Server

Each should have a detailed record page with related information.

## 3.4 Manual actions should create structured events

Example:

A user should not merely type "received 47,500" into a note.

They should create a transaction.

The system can then:

- relate it to client;
- relate it to project;
- generate invoice;
- save PDF;
- update totals;
- create activity;
- send email;
- show it on dashboard.

## 3.5 Default to traceability

For any business-critical object, it should be possible to answer:

- who created it;
- when;
- who last changed it;
- what changed;
- what record it belongs to.

## 3.6 Avoid enterprise cosplay

TattvaTech has four people today.

Version 1 does not need:

- employee attendance;
- payroll;
- complex HR;
- performance scores;
- internal Slack clone;
- 14 layers of approval;
- microservices;
- elaborate workflow builders;
- gigantic business intelligence layer.

The architecture should scale, but the product should still feel fast and simple for four people.

## 4.3 What belongs in MinIO

MinIO stores binary/object files.

Examples:

- generated invoice PDFs;
- quotation files;
- proposal PDFs;
- contracts;
- meeting attachments;
- client files;
- project files;
- screenshots;
- exported reports;
- technical documents.

MySQL should store the pointer to MinIO, not the whole binary file.

## 4.4 MinIO storage placement

On the ROG:

```text
SSD
├── operating system
├── Next.js application
├── MySQL data
└── other latency-sensitive application data

HDD
└── MinIO object data
    ├── invoices/
    ├── quotations/
    ├── proposals/
    ├── contracts/
    ├── clients/
    ├── projects/
    └── internal/
```

MinIO consumes RAM while its process is running, but persistent object data is stored on the configured disk path.

The HDD is appropriate for normal CRM document objects because invoice PDFs and business documents do not require database-grade random I/O performance.

# 6. Authentication and User Accounts

Authentication must be handled inside the Next.js application without introducing a separate authentication platform.

## 6.1 User record

Each user should have at minimum:

- internal ID;
- full name;
- email;
- password hash;
- role ID;
- account status;
- avatar object key if used;
- last login timestamp;
- created at;
- updated at;
- created by;
- disabled at;
- disabled by.

## 6.2 Account status

Allowed states:

- `ACTIVE`
- `INVITED`
- `DISABLED`

Disabled users must not be able to sign in.

Disabling a user must not delete their historical actions.

## 6.3 Password handling

Passwords must never be stored directly.

Requirements:

- hash passwords using a secure server-side password hashing method;
- use per-password salt where applicable;
- never return password hash to UI;
- never write password values to logs;
- password reset must invalidate relevant existing sessions.

## 6.4 Sessions

A session should contain only the minimum necessary identity/session data.

Recommended logical attributes:

- session ID;
- user ID;
- created at;
- expires at;
- revoked at;
- IP metadata if desired;
- basic user-agent metadata if desired.

Session validation occurs server-side.

## 6.5 Login screen

Fields:

- email;
- password.

States:

- default;
- submitting;
- invalid credentials;
- disabled account;
- server failure.

Do not reveal whether a specific email exists when that information is unnecessary.

# 22. Transaction to Invoice Workflow

For a qualifying client payment:

```text
User clicks "New Transaction"
        ↓
Select Payment Received
        ↓
Select Client
        ↓
Select Project / Service
        ↓
Enter amount, date, method, UTR
        ↓
Enable/confirm invoice generation
        ↓
Server validates all fields
        ↓
Create transaction in MySQL
        ↓
Create invoice record
        ↓
Generate invoice document
        ↓
Upload invoice to MinIO
        ↓
Store MinIO object key in invoice record
        ↓
Create activity records
        ↓
Send invoice/payment email via Nodemailer
        ↓
Log email event
        ↓
Show success screen with invoice link
```

## 22.1 Failure handling

Do not report the workflow as fully successful if invoice storage failed.

The server should distinguish:

- transaction saved;
- invoice record created;
- PDF generated;
- MinIO upload succeeded;
- email succeeded.

If email fails:

- transaction and invoice stay valid;
- email event is marked failed;
- user can resend.

If MinIO upload fails:

- invoice must not be marked available;
- system should display an actionable failure;
- retry should be possible without duplicating the transaction.

# 24. Invoice Storage in MinIO

## 24.1 Bucket model

Recommended private bucket:

```text
tattvatech-documents
```

Logical object layout:

```text
invoices/{year}/{month}/{invoice-id}/{filename}
quotations/{year}/{client-id}/{filename}
proposals/{year}/{client-id}/{filename}
contracts/{client-id}/{filename}
clients/{client-id}/{filename}
projects/{project-id}/{filename}
internal/{category}/{filename}
```

## 24.2 Object key requirements

Object keys should:

- be generated server-side;
- avoid using unsanitized user text as the only identifier;
- include stable IDs;
- avoid collisions.

## 24.3 Private access

The MinIO bucket should not be public.

User flow:

```text
User requests file
      ↓
Next.js checks session
      ↓
Next.js checks record permission
      ↓
Application produces controlled file response / temporary access
      ↓
User receives file
```

## 24.4 File metadata in MySQL

Store:

- file record ID;
- object key;
- original filename;
- stored filename;
- MIME type;
- byte size;
- entity type;
- entity ID;
- uploader;
- created at;
- deleted/archived state.

- sending;
- logging;
- failure status;
- resend.

# 38. Website and CRM as Core Firm Services

The company website and CRM are permanent systems.

They should be treated differently from demos.

Rules:

- start automatically after server reboot;
- monitor health;
- avoid resource starvation from demos;
- keep data backed up;
- core service failures take priority over demo workloads.

If a demo threatens core stability, the demo should lose, not the CRM.

# 60. Backups

The ROG server is one machine.

That means it is a single point of physical failure.

Back up:

- MySQL;
- MinIO files;
- configuration required for recovery.

A local backup on the same internal HDD is useful for convenience but is **not sufficient as the only backup**.

At least one backup copy must live off the machine.

## 60.1 Restore goal

The team should know:

- where backups are;
- how to restore MySQL;
- how to restore MinIO;
- how to rebuild the Next.js application;
- which configuration values are required.

A backup that has never been tested is optimism with a filename.

# 62. File Security

1. validate session;
2. load file metadata;
3. load linked entity;
4. check user's permission for that entity;
5. retrieve file;
6. return controlled response.

# 91. Coding Rules for the Build Agent

## 91.1 Do not change architecture casually

If a feature seems difficult, do not solve it by adding an unapproved platform.

The fixed stack remains fixed.

## 91.2 Keep server logic server-side

Never put:

- DB credentials;
- MinIO credentials;
- SMTP credentials;
- permission decisions;

in client code.

## 91.3 Reuse business services

Invoice generation should have one server implementation.

Email sending should have one server mail layer.

Activity creation should have one helper/service.

Permission checks should have one consistent system.

## 91.4 Prefer explicit code

This is an internal operational platform.

Readable, boring code is preferable to clever abstraction that takes thirty minutes to decode.

## 91.5 Avoid premature generic engines

Do not build a universal workflow engine in Version 1.

Implement the actual workflows TattvaTech uses.

# 95. Product North Star

The system should make the following sentence true:

> **If something important happened in TattvaTech, the CRM knows what happened, who did it, what business record it belongs to, what happens next, and where the supporting document lives.**

Not "we probably discussed it on WhatsApp."

Not "Rishit remembers the amount."

The CRM exists to turn TattvaTech's operational memory into structured, searchable, permission-controlled company knowledge.

A user may own a lead but still not be allowed to view company-wide finance.

# 201. Final Instruction to Any Coding Agent

Do not reduce this specification to a generic CRUD dashboard.

The value lies in the relationships and workflows:

```text
Lead
  ↓
Meeting
  ↓
Proposal
  ↓
Won
  ↓
Client
  ↓
Project
  ↓
Payment
  ↓
Invoice
  ↓
MinIO document
  ↓
Email
  ↓
AMC / ongoing relationship
```

and:

```text
Meeting
  ↓
Temporary ERP demo
  ↓
Sales discussion
  ↓
Demo shutdown
```

and:

```text
ROG server
  ↓
Website + CRM + core services
  ↓
Infrastructure visibility
```

Build the system so those flows feel native.

The goal is not to create the largest possible codebase.

The goal is to create the most reliable operational memory TattvaTech can have.
